StockShotGun

A multi-broker trading tool that submits one order and fans it out across 13 brokerage accounts simultaneously. Reverse-split arbitrage (RSA) is the primary use case. This is a map of how it works today.
src/ · Python 3.13 · async-first · generated 2026-05-31, updated 2026-07-02 from live source

The system has six horizontal layers. A request enters through the CLI/TUI/MCP, is picked up by the ExecutionEngine — the single core every adapter sits on top of (ADR 0006) — passes a safety gate (the enforcement layer), is fanned out into one leg per (broker, account) over a BrokerPort, each leg hits a broker integration, and state lands in one of several SQLite stores. A separate signals layer feeds candidate tickers in from the Nasdaq splits calendar. The engine convergence — CLI, TUI, and the agent-facing MCP surface all calling the exact same propose_order/execute_order — is the single most important thing to understand here.

Status: ADR 0006 — Router promoted to ExecutionEngine, cli_bridge.py deleted — is Accepted (2026-07-02) and merged into this branch (PR #3, open). The RSA signals-detection layer (Nasdaq calendar → calendar_signals → promote → buy_signals) shipped to main via PR #2 the same day. This doc reflects that source. 301 tests passing.

02The trade flow — buy / sell

How python src/main.py buy 1 XYZ becomes real orders. The key idea: nothing reaches a broker SDK without first being gated into a proposal and then leg-token validated at the broker boundary.

buy / sell — two-phase propose → execute, on the engine, for every caller
Parse & pre-flight validate. Resolve --broker selection from the registry; engine.validate_targets concurrently validates each broker can authenticate, dropping the ones that can't before gating. CLI, batch, automate, and TUI all call the same method. cli/trade.py run_trade → ExecutionEngine.validate_targets (execution/engine.py:758)
GATE Propose. get_engine() (cli/common.py) returns the lazy singleton ExecutionEngine; engine.propose_order(...) discovers real per-account targets and calls EnforcementCore.propose_order: freeze-list, circuit-breaker, settled-cash/PDT account filter, reconciliation vs stored qty, per-order + daily USD limits, audit integrity check. dry_run is bound into the hashed intent for every caller, not just agents. execution/engine.py:877 propose_order → gate.py:72
MINT One proposal, N leg-tokens. propose_fanout writes one proposals row (self-describing: ticker/side/qty/price/dry_run — ADR 0005) plus one leg_proposals row per target, each with a random 256-bit token bound to the SHA-256 of a single-target intent. Returns a proposal_id. propose_execute.py:229 propose_fanout
Execute (fan-out). engine.execute_order(proposal_id) rebuilds the intent from the stored proposal alone, then asyncio.gathers one place_at_broker call per leg over the BrokerPort. A leg failure does not halt its siblings. render_execution_result (cli/common.py) then renders the engine's native per-leg result into the display shape each adapter expects — counts are per-leg, so a broker with taxable+IRA contributes 2, not 1. execution/engine.py:936 execute_order → cli/common.py render_execution_result
VERIFY Per-leg, at the broker boundary. Each InProcessBroker.place_at_broker reconstructs its single-target intent, hashes it, and consume_leg atomically rejects unless the hash matches its stored token (defense in depth — same check whether in-process or subprocess). A leg addressed to a real account on a spec whose trade fn is account-blind fails cleanly with account_scoped_dispatch_unsupported rather than risking a double-buy. execution/in_process.py place_at_broker → gate.py:173 gate_execute_leg
SDK Place the order. Rate-limit (rate_limiter.wait_if_needed), then call the registry-resolved {broker}Trade(side, qty, ticker, price) — a sync SDK wrapped in asyncio.to_thread. Catch SDK exceptions per leg. in_process.py spec.trade_fn → brokers/<name>.py
Record outcome & aggregate. Each leg writes an execute audit entry (fill qty/price, idempotency key) and updates the circuit breaker. render_execution_result / aggregate_execution_results shape the per-leg results into {successful, failed, skipped} → mapped to an ExitCode (SUCCESS / PARTIAL_BROKER_FAILURE / FULL_BROKER_FAILURE). A rejection (propose-time GateError or execute-time rejected=True) renders as zeros, never a false success. gate.py:207 record_leg_outcome → cli_runtime.py:68 compute_trade_exit_code
--dry-run is a full-pipeline rehearsal, not a readiness check. Since ADR 0006 step 3, --dry-run runs propose_order(dry_run=True) + execute_order(dry_run=True) through the exact same path above — limits, freeze list, reconciliation, and token minting all execute; nothing is placed. The old credentials-only _build_dry_run_readiness short-circuit is deleted.

03The sweep / RSA flow

The reverse-split-arbitrage side runs on a parallel track. You buy fractional shares before a 1:N split; the broker rounds your fraction up to one whole post-split share; sweep detects when that share has arrived and then sells it.

buy --rsa → sweep → sell_arrived
Declare the RSA trade at buy time. buy --rsa --ratio 1:25 writes an rsa_trades row immediately (ratio, expected split date, notes). Positions are not written yet. rsa_store.py · table rsa_trades
Lazy position discovery (ADR 0002). The first sweep --from-trade <id> queries holdings on every enabled broker and, for each (broker, account) showing the ticker, lazy-creates an rsa_positions row with pre_split_qty = observed. Broker Trade() functions only return broker-level success, so per-account fills are discovered later, post-settlement. cli/sweep.py / router/_server.py:266 run_sweep
Classify each position. Compare observed vs pre_split_qty and expected_post_qty = ceil(pre·N/D) → one of AWAITING_SPLIT · PROCESSING · FRACTIONAL_PENDING · SHARE_ARRIVED · AMBIGUOUS · SKIPPED · ERROR. Falls back to the {ticker}D symbol some brokers use post-split. sweep.py:21 SweepStatus · sweep.py:343 classify_holding
Resolve ambiguity with date + profile. When observed == pre == post (e.g. 1 share, 1:25), use BROKER_PROFILES.processing_window_days + expected_split_date (or --force) to decide if the share has arrived. sweep.py:42 BROKER_PROFILES · resolve_ambiguous_with_date
Persist history. Each run upserts sweep_state (latest per position) and appends a sweep_history row — history is never overwritten, status changes print to stdout. sweep_persistence.py:42 persist_sweep_results
Sell what arrived. engine.sell_arrived re-sweeps, groups SHARE_ARRIVED legs by observed qty, and mints one sell proposal per qty group — handing it back to the gate → execute path above for confirmation. execution/engine.py sell_arrived
Two signal feeders into the same buy_signals queue: automation_recap.py parses structured "Recaps" from the RSA community forum, and (shipped 2026-07-02) signals/nasdaq.py polls the Nasdaq splits calendar into calendar_signals, which promote_signal converts into the same buy_signals row shape. Either way, buys land in the watchlist → pending → executed state machine that automate's due-buy path consumes — see the signals flow below. Buys are still human-gated end to end; the recap/calendar parsers stage candidates, a human (or, per the RSA-engine spec, an approval-gated agent) confirms.

03aThe signals flow — calendar → buy queue

Detection is deterministic code with no LLM involvement in what the data is — an agent (or human) only judges whether a detected signal is worth playing.

signals scan → promote → automate due-buy
Fetch & parse. signals scan (CLI) or scan_signals(refresh=true) (MCP) polls the Nasdaq corporate-actions splits calendar and parses reverse splits (ratio N:D, N<D) into CalendarSignal objects. Malformed rows are skipped, never fatal — a fetch failure returns a structured error rather than raising. signals/nasdaq.py fetch_splits_calendar · parse_splits_payload
Idempotent upsert. Hits land in calendar_signals (in the same automation.sqlite3 as everything else). Re-scanning bumps last_seen only — dismissed/promoted/expired rows are never resurrected. A signal whose effective date passes without action auto-expires on the next scan. automation_recap.py upsert_calendar_signals · expire_stale_calendar_signals
Evaluate & promote or dismiss. A human or agent reviews `new` signals (price sanity, ratio worth playing, settlement timing) and either promote_signals it into the actionable buy_signals queue, or dismiss_signals it with a reason — the audit trail for why a play was skipped. Promote refuses non-`new` signals; a NULL effective date is treated as immediately due. automation_recap.py promote_calendar_signal → router tools promote_signal · dismiss_signal
Consumed by automate. Promoted signals are ordinary buy_signals rows — the existing due-buy path picks them up on its normal cadence and drives them through the gate → execute flow above, same as a recap-sourced signal. cli/automate.py

06Decisions that shaped this (ADRs)

ADRDecisionWhy it matters for a rethink
0001Per-account position granularityA broker can hold multiple accounts (taxable + IRA) that split differently. Position = one (broker, account), not one broker.
0002Lazy position discoveryPositions are discovered on first sweep, not at buy — because buys don't return per-account fills and a post-buy query races settlement.
0003MCP fan-out: per-broker MCPs + router + per-leg tokensThe big one. Reframed the tool for the agentic era: one fan-out call is the differentiator. Introduced the in-process/subprocess duality and per-leg token model.
0004Broker registry as single source of truthCollapsed 5 duplicated broker enumerations into one lazy registry. Importing it imports no SDK; a subprocess resolves only its own broker.
0005Self-describing proposal (delete router intent cache)Order params now live on the proposal row, so execute works across restarts/processes from proposal_id alone. Removed a fragile in-memory sidecar.
0006Execution engine as core — Router promoted to ExecutionEngine, cli_bridge deletedAccepted 2026-07-02. Closes the tension below: CLI/TUI/MCP are now provably thin adapters over one engine, one propose path, one result type. Fixed two real bugs the hand-rolled bridge path had (single-"primary"-leg fan-out, --dry-run never reaching the gate).

07Tensions & rethink candidates

This is the payload. These are the places where the current shape is in friction with itself — the questions worth answering before you redraw the architecture. Severity reflects how much it constrains future change, not how broken it is.

The agentic router was load-bearing for the non-agentic CLI resolved

ADR 0003 framed the MCP layer as the agent-facing surface, with per-broker MCPs as "implementation detail." But cli_bridge.apply_main_py_gate + execute_via_router routed the plain CLI's buy/sell through the same Router singleton and MCP place_at_broker path by hand — and diverged from the agent path doing it: one synthetic BrokerAccount(broker,"primary") leg (bypassing per-account fan-out, ADR 0001), and --dry-run short-circuiting to a credentials-only readiness check that never touched the enforcement pipeline.

Resolved by naming the Router the core execution engine outright, not an agent adapter.

✓ Shipped — ADR 0006: Execution Engine as Core Accepted 2026-07-02

Router was promoted to execution/engine.py::ExecutionEngine (class body relocated, not just renamed — the import direction is now genuinely one-way: agentic/ → execution/ → enforcement/, locked by tests/test_execution_layering.py across both packages). The misnamed BrokerMCPServer split behind a BrokerPort protocol into InProcessBroker (engine-owned) and SubprocessBrokerProxy (agentic-owned MCP transport). cli_bridge.py is deleted — grep -rn cli_bridge src tests returns zero. --dry-run is now a full-pipeline rehearsal (limits/freeze/reconciliation/token-minting all run, nothing is placed) instead of a credentials-only check. All six migration steps shipped incrementally behind the Router = ExecutionEngine alias, each landing with the full suite green; 301 tests pass today (was 258 at the start of this plan, 213 before ADR 0006 began).

Account-scoped dispatch: TradeFn is account-blind, so per-account fan-out is guard-railed, not real, for every broker but the placeholder case med

ADR 0006 gave every caller real per-account discovery — but TradeFn(side, qty, ticker, price) takes no account parameter, so a broker can't actually be told which account to trade in. Fennel's trade fn fans out internally over all session accounts, so under naive per-account fan-out it would multiply into N² live orders; it's now pinned multi_account=False as a stopgap. A structural guard in InProcessBroker.place_at_broker rejects any leg addressed to a real (non-"primary") account on a spec without an explicit account_scoped_trade flag — provably inert today (every current broker's real legs are all "primary") but load-bearing the moment a second multi-account broker shows up.

Threading account_id through TradeFn is the documented long-term fix (ADR 0006 open questions) — until then, "per-account fan-out" is a safety guarantee (never double-buy) rather than a fully-realized capability (route to a specific account).

Fill-vs-marking crash window in automate low

automate marks a signal executed immediately after its order's execute_order returns. A crash between the broker fill and mark_buy_signals_executed would leave a filled order's signal sitting pending, re-executing (double-trade) on the next run. Mitigated but not eliminated: signals are now marked incrementally per-order rather than in one bulk pass after the whole batch, so a mid-batch abort only exposes the crash window for the order in flight, not the entire batch.

ADR 0006's candidate fix — a persisted executing state written before dispatch, so a crash surfaces as "needs manual reconciliation" instead of silently re-executing — is still open.

Dual broker layer: brokers/* functions and InProcessBroker wrapping them med

Each broker is described twice — once as raw async functions in brokers/<name>.py (resolved via registry string refs), and again as a uniform runtime wrapper (execution/in_process.py::InProcessBroker, post-ADR-0006) implementing place_at_broker / get_holdings_at_broker / list_accounts_at_broker / health_check. Rate limits live in base.py and the registry owns everything else (ADR 0004 explicitly left rate limits out). Two enumerations of broker capability that must stay in sync.

Should the BrokerSpec own rate limits too, closing the last gap in "single source of truth"? And is the BrokerPort-wrapper-per-broker earning its keep in in-process mode, or is it ceremony around a plain function call?

Two deployment shapes, one trust model to maintain med

In-process (1 process, fast) vs subprocess (14 processes, isolated). ADR 0003's elegance is that place_at_broker validates identically in both — but you still carry the SubprocessBrokerProxy stdio plumbing, FastMCP result-unwrapping quirks, and a second failure surface for a mode that may rarely run. For a single-user tool on one machine, is the subprocess mode a real requirement or a someday?

Is blast-radius isolation across 14 processes worth its complexity for your actual deployment (one operator, one box)? If not, the in-process path could be the only path and the proxy retired.

The propose/execute + per-leg-token + audit machinery may be over-built for one user med

Two-phase proposals, 256-bit single-use tokens per leg, intent-hash binding, 300s TTL, detect-and-drop schema migrations, idempotency keys, integrity-checked audit log. This is genuinely good engineering — it's also a lot of safety apparatus for a tool one person runs by hand. Much of it exists to make the agent path safe (don't let an LLM double-submit). The cost is real: schema migrations that drop rows, multiple SQLite files, and a proposal-cleanup obligation that's been deferred twice.

Separate the question: which safety properties protect against broker/network failure (keep — circuit breaker, reconciliation, limits) vs which protect against an untrusted caller (tokens, intent hashing)? If the only caller is you + a trusted agent, the second set could shrink dramatically.

Persistence is scattered across stores with no shared cleanup low

Four stores (proposals, audit, RSA/automation, MCP logs), three file formats (sqlite ×2, jsonl ×2), three lifecycles. Proposal rows "linger past TTL until a future cleanup job" (ADR 0005 admits this). No single place answers "what's the state of the world right now."

Would one durable store with a clear schema + a retention policy beat four ad-hoc ones? Or at least: who owns proposal-row GC, and when does it ship?

main.py still carries inline business logic low

The cli/ split moved trade/sweep/automate/batch/signals/status out, but health and holdings handlers (and all argparse construction) still live inline in the ~800-line main.py, including Webull-specific health probing. The dispatch is a chain of if args.action == ….

Finish the extraction — a uniform command registry ({action → handler}) would let main.py shrink to parse → dispatch → render, matching the cleanliness of the layers below it.

Fan-out concurrency is real but capped by sync SDKs + a global rate limiter low

Legs run via asyncio.gather, but most broker SDKs are synchronous and run in asyncio.to_thread (thread-pool + GIL), and a single global rate_limiter serializes per broker. Browser brokers (Wells Fargo, Chase) are far slower than the API ones. "Simultaneous" is true at the dispatch layer; wall-clock is gated by the slowest broker.

For RSA, submission simultaneity is the whole point. Worth measuring actual leg-dispatch skew — and deciding whether browser brokers belong on the same hot path as API brokers or on a separate, slower track.

The big one — Router as the single execution core with CLI/TUI/MCP as thin adapters — shipped as ADR 0006. If you want, I can take any of the remaining tensions and spin it into a concrete redesign, or generate this map as an editable diagram (Mermaid/SVG) you can mark up.
