StockShotGun

A multi-broker trading tool that submits one order and fans it out across 13 brokerage accounts simultaneously. Reverse-split arbitrage (RSA) is the primary use case. This is a map of how it works today — built to help rethink the architecture.
src/ · Python 3.13 · async-first · generated 2026-05-31 from live source

The system has five horizontal layers. A request enters through the CLI/TUI, passes a safety gate (the enforcement layer), is fanned out by the agentic router into one leg per (broker, account), each leg hits a broker integration, and state lands in one of several SQLite stores. The same router/gate path serves both the human CLI and the agent-facing MCP surface — that convergence is the single most important thing to understand here.

Heads-up: the repo's CLAUDE.md describes an older flat layout (brokers/ + tui/ at root, "12 brokers", OrderBatchProcessor). That's stale. The real tree is a layered src/ with enforcement/, agentic/, cli/ packages, 13 brokers, and the OrderBatchProcessor has been retired in favor of the router. This doc reflects the current source.

02The trade flow — buy / sell

How python src/main.py buy 1 XYZ becomes real orders. The key idea: nothing reaches a broker SDK without first being gated into a proposal and then leg-token validated at the broker boundary.

buy / sell — two-phase propose → execute
Parse & pre-flight validate. Resolve --broker selection from the registry; concurrently validate each broker can authenticate, dropping the ones that can't before gating. cli/trade.py:34 run_trade → cli_bridge.preflight_validate:219
GATE Propose. apply_main_py_gate lazily builds the singleton Router, then calls EnforcementCore.propose_order: freeze-list, circuit-breaker, settled-cash/PDT account filter, reconciliation vs stored qty, per-order + daily USD limits, audit integrity check. cli_bridge.py:66 → gate.py:72 propose_order
MINT One proposal, N leg-tokens. propose_fanout writes one proposals row (self-describing: ticker/side/qty/price/dry_run — ADR 0005) plus one leg_proposals row per target, each with a random 256-bit token bound to the SHA-256 of a single-target intent. Returns a proposal_id. propose_execute.py:229 propose_fanout
Execute (fan-out). execute_via_router → Router.execute_order(proposal_id) rebuilds the intent from the stored proposal alone, then asyncio.gathers one place_at_broker call per leg. A leg failure does not halt its siblings. cli_bridge.py:290 → router/_server.py:758 execute_order
VERIFY Per-leg, at the broker boundary. Each BrokerMCPServer.place_at_broker reconstructs its single-target intent, hashes it, and consume_leg atomically rejects unless the hash matches its stored token (defense in depth — same check whether in-process or subprocess). _base.py:207 place_at_broker → gate.py:173 gate_execute_leg
SDK Place the order. Rate-limit (rate_limiter.wait_if_needed), then call the registry-resolved {broker}Trade(side, qty, ticker, price) — a sync SDK wrapped in asyncio.to_thread. Catch SDK exceptions per leg. _base.py:280 spec.trade_fn → brokers/<name>.py
Record outcome & aggregate. Each leg writes an execute audit entry (fill qty/price, idempotency key) and updates the circuit breaker. Results aggregate into a legacy {successful, failed, skipped} shape → mapped to an ExitCode (SUCCESS / PARTIAL_BROKER_FAILURE / FULL_BROKER_FAILURE). gate.py:207 record_leg_outcome → cli_runtime.py:68 compute_trade_exit_code

03The sweep / RSA flow

The reverse-split-arbitrage side runs on a parallel track. You buy fractional shares before a 1:N split; the broker rounds your fraction up to one whole post-split share; sweep detects when that share has arrived and then sells it.

buy --rsa → sweep → sell_arrived
Declare the RSA trade at buy time. buy --rsa --ratio 1:25 writes an rsa_trades row immediately (ratio, expected split date, notes). Positions are not written yet. rsa_store.py · table rsa_trades
Lazy position discovery (ADR 0002). The first sweep --from-trade <id> queries holdings on every enabled broker and, for each (broker, account) showing the ticker, lazy-creates an rsa_positions row with pre_split_qty = observed. Broker Trade() functions only return broker-level success, so per-account fills are discovered later, post-settlement. cli/sweep.py / router/_server.py:266 run_sweep
Classify each position. Compare observed vs pre_split_qty and expected_post_qty = ceil(pre·N/D) → one of AWAITING_SPLIT · PROCESSING · FRACTIONAL_PENDING · SHARE_ARRIVED · AMBIGUOUS · SKIPPED · ERROR. Falls back to the {ticker}D symbol some brokers use post-split. sweep.py:21 SweepStatus · sweep.py:343 classify_holding
Resolve ambiguity with date + profile. When observed == pre == post (e.g. 1 share, 1:25), use BROKER_PROFILES.processing_window_days + expected_split_date (or --force) to decide if the share has arrived. sweep.py:42 BROKER_PROFILES · resolve_ambiguous_with_date
Persist history. Each run upserts sweep_state (latest per position) and appends a sweep_history row — history is never overwritten, status changes print to stdout. sweep_persistence.py:42 persist_sweep_results
Sell what arrived. Router.sell_arrived re-sweeps, groups SHARE_ARRIVED legs by observed qty, and mints one sell proposal per qty group — handing it back to the gate → execute path above for confirmation. router/_server.py:498 sell_arrived
Feeder, not yet wired to auto-execution: automation_recap.py parses structured "Recaps" from the RSA community forum into buy/sell signals (a watchlist → pending → executed state machine in automation.sqlite3). Today buys are still kicked off manually; the recap parser proposes, a human confirms.

06Decisions that shaped this (ADRs)

ADRDecisionWhy it matters for a rethink
0001Per-account position granularityA broker can hold multiple accounts (taxable + IRA) that split differently. Position = one (broker, account), not one broker.
0002Lazy position discoveryPositions are discovered on first sweep, not at buy — because buys don't return per-account fills and a post-buy query races settlement.
0003MCP fan-out: per-broker MCPs + router + per-leg tokensThe big one. Reframed the tool for the agentic era: one fan-out call is the differentiator. Introduced the in-process/subprocess duality and per-leg token model.
0004Broker registry as single source of truthCollapsed 5 duplicated broker enumerations into one lazy registry. Importing it imports no SDK; a subprocess resolves only its own broker.
0005Self-describing proposal (delete router intent cache)Order params now live on the proposal row, so execute works across restarts/processes from proposal_id alone. Removed a fragile in-memory sidecar.

07Tensions & rethink candidates

This is the payload. These are the places where the current shape is in friction with itself — the questions worth answering before you redraw the architecture. Severity reflects how much it constrains future change, not how broken it is.

The agentic router is load-bearing for the non-agentic CLI high

ADR 0003 framed the MCP layer as the agent-facing surface, with per-broker MCPs as "implementation detail." But cli_bridge.apply_main_py_gate + execute_via_router route the plain CLI's buy/sell through the same Router singleton and MCP place_at_broker path. So "the agentic layer" is no longer optional — it's the only execution path. A human typing buy 1 XYZ is paying for MCP-shaped indirection (router → BrokerMCPServer → spec.trade_fn).

Is the Router the core execution engine (and the CLI/TUI/MCP are all just adapters onto it), or is it an agent adapter that the CLI shouldn't depend on? Pick one and name it. The current code wants the first; the ADR language implies the second.

↳ Redesign drafted — ADR 0006: Execution Engine as Core

Verified the friction is real, not cosmetic: the main CLI/TUI reach the Router through cli_bridge, which reimplements the propose half by hand and diverges from the agent path — it hardcodes one synthetic BrokerAccount(broker,"primary") leg (bypassing per-account fan-out, ADR 0001), and its --dry-run short-circuits to a credentials-only readiness check that never touches the enforcement pipeline. The fix: promote Router → execution/ExecutionEngine, split the misnamed BrokerMCPServer behind a BrokerPort protocol so the engine never imports agentic/, and delete cli_bridge. Six incremental steps behind a Router alias.

Dual broker layer: brokers/* functions and BrokerMCPServer wrapping them med

Each broker is described twice — once as raw async functions in brokers/<name>.py (resolved via registry string refs), and again as a uniform 4-tool MCP server in agentic/_base.py. Rate limits live in base.py and the registry owns everything else (ADR 0004 explicitly left rate limits out). Two enumerations of broker capability that must stay in sync.

Should the BrokerSpec own rate limits too, closing the last gap in "single source of truth"? And is the MCP-server-per-broker wrapper earning its keep in in-process mode, or is it ceremony around a plain function call?

Two deployment shapes, one trust model to maintain med

In-process (1 process, fast) vs subprocess (14 processes, isolated). ADR 0003's elegance is that place_at_broker validates identically in both — but you still carry the SubprocessBrokerProxy stdio plumbing, FastMCP result-unwrapping quirks, and a second failure surface for a mode that may rarely run. For a single-user tool on one machine, is the subprocess mode a real requirement or a someday?

Is blast-radius isolation across 14 processes worth its complexity for your actual deployment (one operator, one box)? If not, the in-process path could be the only path and the proxy retired.

The propose/execute + per-leg-token + audit machinery may be over-built for one user med

Two-phase proposals, 256-bit single-use tokens per leg, intent-hash binding, 300s TTL, detect-and-drop schema migrations, idempotency keys, integrity-checked audit log. This is genuinely good engineering — it's also a lot of safety apparatus for a tool one person runs by hand. Much of it exists to make the agent path safe (don't let an LLM double-submit). The cost is real: schema migrations that drop rows, multiple SQLite files, and a proposal-cleanup obligation that's been deferred twice.

Separate the question: which safety properties protect against broker/network failure (keep — circuit breaker, reconciliation, limits) vs which protect against an untrusted caller (tokens, intent hashing)? If the only caller is you + a trusted agent, the second set could shrink dramatically.

Persistence is scattered across stores with no shared cleanup low

Four stores (proposals, audit, RSA/automation, MCP logs), three file formats (sqlite ×2, jsonl ×2), three lifecycles. Proposal rows "linger past TTL until a future cleanup job" (ADR 0005 admits this). No single place answers "what's the state of the world right now."

Would one durable store with a clear schema + a retention policy beat four ad-hoc ones? Or at least: who owns proposal-row GC, and when does it ship?

main.py still carries inline business logic low

The cli/ split moved trade/sweep/automate/batch out, but health and holdings handlers (and all argparse construction, ~250 lines) still live inline in the 755-line main.py, including Webull-specific health probing. The dispatch is a chain of if args.action == ….

Finish the extraction — a uniform command registry ({action → handler}) would let main.py shrink to parse → dispatch → render, matching the cleanliness of the layers below it.

Fan-out concurrency is real but capped by sync SDKs + a global rate limiter low

Legs run via asyncio.gather, but most broker SDKs are synchronous and run in asyncio.to_thread (thread-pool + GIL), and a single global rate_limiter serializes per broker. Browser brokers (Wells Fargo, Chase) are far slower than the API ones. "Simultaneous" is true at the dispatch layer; wall-clock is gated by the slowest broker.

For RSA, submission simultaneity is the whole point. Worth measuring actual leg-dispatch skew — and deciding whether browser brokers belong on the same hot path as API brokers or on a separate, slower track.
