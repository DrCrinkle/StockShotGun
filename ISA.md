# StockShotGun — Agentic Architecture ISA

> First-cut project ISA. This is a design articulation, not an implementation plan. The ideal-state articulated here becomes the project's long-lived system of record as the codebase evolves toward it.

## Problem

StockShotGun was designed before agentic AI was a usable surface. It's a Python CLI/TUI with 12 broker integrations (Robinhood, Tradier, TastyTrade, Public, Firstrade, Fennel, Schwab, BBAE, DSPAC, SoFi, Webull, Wells Fargo) that fans an order out to many brokerage accounts simultaneously — the original goal — but every decision in the loop requires a human: when to buy, when to sweep, when to sell, how to interpret per-broker settlement states post-reverse-split. The RSA workflow has persistence (`rsa_store`, `sweep_persistence`) and a sweep CLI but the agentic glue is missing.

Robinhood just shipped an official MCP server for agentic trading (2026-05). That collapses one broker behind an agent surface. StockShotGun's latent value proposition in the agentic era is strictly stronger: **one MCP surface that fans out across 12 brokers** is more useful than 12 isolated broker MCPs, because the coordination problem — same ticker, same intent, simultaneous fire across all enabled accounts — is exactly what the project already solves.

The current shape doesn't expose any of that to agents. An agent can shell out to `python3 main.py buy ...`, but it can't inspect what brokers are enabled, can't dry-run an order, can't propose-then-confirm, can't see structured holdings data, and can't safely participate in the RSA decision loop without the human reading sweep output and deciding by hand.

## Vision

**Architecture** (resolved 2026-05-27): twelve per-broker MCP servers + one thin router MCP + one shared `enforcement/` library that every order path imports. Each per-broker MCP owns its own credentials, rate limiter, circuit breaker, and observability surface — one auth-refresh bug or a broker outage isolates to that broker only. The router MCP is the agent's primary surface: it exposes the fan-out tools (`place_order`, `get_holdings`, `run_sweep`) and the agent never sees the twelve underlying processes. The CLI, the TUI, the router MCP, and each per-broker MCP all import the same `enforcement` module and call `gate_order(...)` before any live broker action — so dollar limits, dry-run defaults, confirmation-token validation, intent-binding hash, idempotency keys, and the tamper-evident audit log are enforced once and uniformly. The RSA workflow becomes an agent loop driving the router: agent watches `expected_split_date`, runs sweeps, classifies positions, proposes sells when broker-specific settlement windows allow, principal confirms. The euphoric surprise: the same broker code that took a year of broker-by-broker SDK work now powers a 60-second agent demo where Claude buys $50 of TSLA across four accounts via one router call, dry-running first, with per-broker failures isolated and the live order rejected if any safety gate trips.

## Out of Scope

- **Autonomous unsupervised trading.** Every irreversible action (live order, live sell) requires explicit principal confirmation via the propose/execute confirmation-token pattern. Agents do not place live orders without a human in the loop in v1.
- **Removing the CLI or TUI.** The CLI is the deterministic backbone and the manual-mode escape hatch. MCP is additive.
- **Exposing per-broker MCPs directly to agents.** The implementation uses per-broker MCPs for isolation, but the agent's primary surface is the router MCP — the fan-out is the value prop and the agent should not have to coordinate across twelve endpoints. Direct per-broker MCP access stays available for debugging and CLI tooling but is not part of the documented agent contract.
- **A web UI or dashboard.** The interface stack stays CLI + TUI + MCP for this project. A future dashboard is a separate project that consumes the router MCP as a client — it does not need its own broker integrations or its own enforcement layer, which is one of the leverage payoffs of putting MCP at the boundary here.
- **Strategy backtesting, indicator pipelines, market-data streaming.** This is an order-routing + RSA-coordination tool. Quote/feed engines are someone else's problem.
- **Non-equity assets** (options, futures, crypto). Equities only in v1.
- **Multi-tenant operation.** This is a single-principal tool. No user accounts, no auth-as-a-service.
- **Bun/TypeScript rewrite.** This is the one Python project in Taylor's stack; the broker SDK ecosystem is Python-native and rewriting 12 integrations to chase language uniformity is value-negative.

## Principles

- **Code enforces safety, prompts do not.** Dollar limits, dry-run defaults, confirmation-token TTLs live in deterministic Python — not in the agent's system prompt. Treat the agent as untrusted code calling a trusted boundary.
- **One canonical execution path.** CLI, TUI, MCP all route through the same `brokers/` layer. There is exactly one place where an order becomes a real broker call. Surfaces are thin shells.
- **Fail loudly, individually.** A single broker failure during fan-out does not halt the batch — and it does not get silently swallowed. The shape of the response always tells the agent (and the user) which brokers succeeded and which did not, with reasons.
- **Reversible vs irreversible asymmetry.** Reads, dry-runs, sweeps, holdings queries: build over ask. Live orders, live sells, live cancels: always ask, always confirm, always log.
- **The boundary is explicit.** What the agent decides (when, what, how much, which brokers) is named in prose; what the executor enforces (limits, redaction, idempotency) is named in code. The doc and the code agree on where the line is.

## Constraints

- **Python 3.13+, async-first.** The existing broker integrations are async; the MCP server must be async-native too. No mixing sync MCP frameworks with async broker calls.
- **Reuse `src/brokers/` unchanged.** Twelve broker integrations are a year of work and represent the project's moat. The MCP layer wraps them; it does not replace, rewrite, or fork them.
- **Persistence stays SQLite via `rsa_store.py` and `sweep_persistence.py`.** Schema, lazy-position-discovery semantics, and the per-account Position granularity from ADRs 0001/0002 are immovable.
- **Rate limiting and HTTP-client pooling from `brokers/base.py` apply on every code path.** The MCP server must call broker functions through the existing primitives; it does not get its own HTTP client.
- **Credentials never leave the process.** No MCP response, log line, or error message contains broker credentials, session tokens, OAuth tokens, cookies, or refresh tokens.
- **MCP server is localhost-only by default.** Network exposure is opt-in, behind an explicit env var, with a bearer token requirement. Default deployment is local stdio.
- **No new persistence outside the broker/RSA primitives.** The MCP server does not introduce its own database. State lives in the existing tables.

## Goal

Expose the existing 12-broker fan-out via a router MCP backed by twelve per-broker MCPs sharing one `enforcement/` library. The router is the agent's surface; the per-broker MCPs isolate blast radius and credentials; the enforcement library is the single source of truth for safety gates (dollar limits, dry-run defaults, intent-binding confirmation tokens with idempotency keys, reconciliation, corporate-action freeze, circuit breaker, settled-cash check, tamper-evident audit log). CLI and TUI route through the same enforcement library so limits never drift across surfaces. Document an RSA agent workflow that drives the buy → sweep → sell loop through router read tools and the confirmation-gated write tools. Ship the design first (this ISA), then implementation in subsequent tasks.

## Decisions

- **2026-05-27 — One fan-out MCP, not twelve per-broker MCPs.** Per-broker MCPs would push the coordination problem back onto the agent, exactly the problem StockShotGun was built to solve. The fan-out is the value prop. Recorded for ADR 0003.
- **2026-05-27 — Propose/execute pattern with single-use TTL tokens.** Considered alternatives: (a) every order tool takes a `confirmation: true` arg — rejected, prompt-injectable; (b) out-of-band confirmation (SMS/push) — rejected, too heavy for v1; (c) human-in-CLI confirms via TUI before MCP executes — rejected, breaks the agent loop. Propose/execute with code-enforced TTL is the smallest deterministic safety primitive that doesn't depend on the agent's good behavior.
- **2026-05-27 — Stay in Python.** Considered porting broker layer to TypeScript for tooling uniformity. Rejected: 12 broker SDKs are Python-native, `zendriver` browser automation for Wells Fargo is Python, the value is in the integrations not the orchestration language. The one-Python-project exception in Taylor's stack is earned.
- **2026-05-27 — CLI/TUI stay unchanged.** Considered a CLI rewrite that becomes a thin MCP-client. Rejected for v1: the CLI is the deterministic escape hatch when the agent layer misbehaves, and rewriting it doubles the v1 scope.
- **2026-05-27 — Localhost-stdio MCP default.** Considered HTTP+auth from the start. Rejected: stdio is the lowest-attack-surface default, Claude Desktop and most agent runners speak it natively, and we can add HTTP later without breaking the stdio contract.
- **2026-05-27 — Advisor pass surfaced FIVE issues against the initial design (commitment-boundary call):**
  1. Confirmation-token TTL alone is insufficient — needs intent-binding hash + idempotency keys. Resolved by ISC-39 and ISC-40.
  2. **Monolithic fan-out MCP vs per-broker MCPs + router is a PENDING DECISION.** Advisor argued for per-broker isolation (blast radius, credential isolation, per-broker semantics, observability) with a thin aggregator/router exposing the fan-out surface. The agent-facing tool stays the same shape; the implementation becomes N+1 processes. Counterargument (original): one process is simpler to deploy/operate and the broker layer is already unified in Python. **NOT YET DECIDED — principal review required before BUILD.** ADR 0003 will not be written until this fork is resolved.
  3. Missing safety gates surfaced: reconciliation, corporate-action freeze, circuit breaker, settled-cash/PDT, tamper-evident audit log, idempotency keys, intent-binding hash. All now added as ISC-39 through ISC-47.
  4. **CLI/TUI vs MCP enforcement split** — keeping CLI unchanged while adding MCP safety means limits live in two places and will drift. ISC-46 captures the fork: either route both through a shared enforcement core (more work, safer) or document CLI as a privileged unguarded surface (less work, documented gap). **PENDING — principal review.**
  5. RSA agent loop needs explicit termination conditions (max iter, max spend, max wall-clock). Added as ISC-47.
- **2026-05-27 — Fork 1 RESOLVED — per-broker MCPs + router.** Principal accepted Advisor's recommendation. Architecture is: twelve per-broker MCP processes (one per broker, each owning its credentials/rate-limiter/circuit-breaker) + one router MCP exposing fan-out tools to agents + one `enforcement/` library all paths import. Agent's primary surface is the router. ADR 0003 will document this. ISCs reshaped accordingly (ISC-3 split into 3, 3.1, 3.2; ISC-4 added 4.1; ISC-10 added 10.1, 10.2).
- **2026-05-27 — Fork 2 RESOLVED — shared enforcement core.** Principal chose: CLI, TUI, router MCP, and per-broker MCPs all import `src/enforcement/` and call `gate_order(...)` before any live broker action. No drift, no privileged unguarded surface. Static check in the build asserts every broker call site is preceded by an enforcement gate. New feature F0-EnforcementCore is the highest-priority work item; F5 becomes the wiring task. ISC-46 reframed from anti-with-pending to positive (route through shared module), ISC-46.1 added as the anti-criterion form.
- **2026-05-27 — Architecture implications of the two resolutions.** F0-EnforcementCore is the new critical-path feature — it must land before F2a/F2b are usable. The 12-way per-broker MCP fan-out (F2a) is parallelizable. Defense in depth: per-broker MCPs re-validate enforcement even though the router already gated — they do not trust their caller. The `enforcement/` library is a Python module imported in-process; it is NOT a separate service (rejected: another process boundary buys nothing here when the gate is deterministic Python).
- **2026-05-27 — Prior PAI work referenced.** `MEMORY/WORK/20260401-120000_auto-rsa-reference-implementation-study` (auto-rsa reference implementation analysis), `MEMORY/broker_settlement_tiers.md`, `MEMORY/rsa_capture_at_buy_time.md` already inform the broker-specific RSA semantics that ISC-22 + ISC-42 must respect. Architecture choices for the agent loop should preserve the lazy-position-discovery semantics from ADRs 0001/0002.
